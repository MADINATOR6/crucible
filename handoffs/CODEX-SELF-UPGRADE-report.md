## 2. What is wrong or fragile today?

1. **VERIFIED in the current launcher — a successful run can trigger a quota reset.** The launcher searches all collected errors and every stderr line for quota phrases. Any match can set exit 4 and record provider unavailability, even when the process exited zero, emitted `turn.completed`, and produced a report. Upstream can emit an `error` event and keep processing. Crucible already tests a recovered 503. Add the equivalent recovered-quota fixture and retain a terminal-quota fixture. A separate read-only check of the actual regex matched `Usage limit reached` and did not match `Your API project has reached its spend limit.` The latter is a billing condition with different recovery semantics. **UNVERIFIED:** whether a real dispatch has suffered the false reset. [Quota scan](/C:/Users/Madison/code/claude-codex-collab/scripts/codex-dispatch.ps1:609) · [Exit classification](/C:/Users/Madison/code/claude-codex-collab/scripts/codex-dispatch.ps1:646) · [State update](/C:/Users/Madison/code/claude-codex-collab/scripts/codex-dispatch.ps1:696) · [Upstream event handling](/C:/Users/Madison/code/claude-codex-collab/ext/codex-ref/codex-rs/exec/src/event_processor_with_jsonl_output.rs:451)
2. **VERIFIED — token accounting needs attention before adding resume.** Tagged 0.172.0 emits the latest **thread total** at completion and emits zeroes when it has received no usage update. Crucible sums completion records and adds the result to the task. Its fixture even supplies two completion records. With resume, adding an entire thread total again could count the previous dispatch twice. Record the previous total for that thread and test the delta before enabling resume. Current single-turn dispatches were not shown to overcount.
